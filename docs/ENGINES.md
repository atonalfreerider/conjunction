# Shared engines (`android/core`, mirrored by `ios/Sources/ConjunctionCore`)

`:core` is a plain Kotlin/JVM module. It uses `java.time` only, has no Android APIs, and has no
third-party runtime dependencies. Package root: `com.metavirtuoso.conjunction.core`. The Android
app depends on `project(":core")`. The Swift package ports the same algorithms and bundles the
**same resource files** byte-for-byte. Both test suites read the same golden files in `testdata/`.

```
cd android && ./gradlew :core:test          # JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64 (set in gradle.properties)
./gradlew :core:writeGoldens                # regenerate golden_compat.json + golden_prompts.json from Kotlin
```

Typical app flow:

```kotlin

val chart = NatalChart.compute(birth)                    // whole-sign houses
val chinese = ChineseZodiac.compute(birth)

val text = ReadingCleaner.clean(modelAnswer) ?: FallbackReadings.daily(chart, transits, today)
```

## Astronomy

Positions are apparent, geocentric, tropical, on the **true ecliptic and equinox of date**, which
is what Swiss Ephemeris returns by default and what astrologers expect.

* **Time.** UT is taken as UTC. TT = UT + ΔT, where ΔT is linearly interpolated in the bundled
  Swiss Ephemeris table for 1900-2101; outside that range the Espenak-Meeus polynomials are used.
  Using Swiss Ephemeris' own ΔT means the Moon (about 0.5″ per second of ΔT error) matches the
  reference even for future dates.
* **Sun, Mercury-Neptune.** VSOP87D (heliocentric, ecliptic of date). Terms are kept when
  `|A| * 0.11^power >= 2e-7` rad (L, B), or `2e-7 * a` AU for R. A light-time iteration places
  **both** the planet and the Earth at `t - τ`, which also applies annual aberration (Meeus ch. 33).
  Then the FK5 correction (Meeus 32.3) and nutation in longitude are applied.
* **Moon.** Meeus ch. 47 (ELP-2000/82, 60 + 60 terms, plus the A1/A2/A3 additive terms) and
  nutation.
* **Pluto.** Meeus ch. 37 (J2000 heliocentric; valid 1885-2099, still accurate in 2100), rigorously
  precessed to the ecliptic of date (Meeus 21.5) before the geocentric transformation.
* **Nutation.** IAU 1980 leading terms (Meeus ch. 22 short form, under 0.5″). True obliquity is
  ε0 (Meeus 22.2) + Δε.
* **Speed and retrograde.** Central difference over ±0.05 day. `retrograde = speed < 0`.
* **Sidereal time.** GMST (Meeus 12.4) plus the equation of the equinoxes.
* **Angles.** MC = atan2(sin RAMC, cos RAMC cos ε). Asc = atan2(cos RAMC, -(sin ε tan φ + cos ε sin RAMC)).
  Inside the polar circles (|φ| ≥ 90° − ε) the Ascendant is flipped by 180° when it would fall in
  the western half, as Swiss Ephemeris does.
* **Houses.** **Whole sign** is the default: house 1 is the Ascendant's sign, each later sign is the
  next house, and a body's house is its sign's distance from the rising sign. **Placidus** uses
  semi-arc fixed-point iteration for cusps 11, 12, 2 and 3 (converging to 1e-9°); the others are the
  angles or opposite cusps. Placidus is undefined for |φ| ≥ 90° − ε, so the engine falls back to
  **Porphyry** there and sets `housesFellBack = true`. Porphyry is also available directly.
* **Aspects (natal).** Conjunction 8°, sextile 5°, square 7°, trine 7°, opposition 8° (each
  widened by 2° when the Sun or Moon is involved). The tightest aspect per pair counts. `applying`
  compares the orb now with the orb 0.01 day later. Transit-to-natal aspects use half those orbs.

### Measured accuracy (testdata/golden_charts.json, 50 charts 1900-2100)

The reference is Swiss Ephemeris 2.10.03 with its `sepl_18`/`semo_18` data files (SWIEPH, not
Moshier).

| quantity | contract | measured worst |
|---|---|---|
| Sun … Pluto longitudes (500 values) | ≤ 0.05° | **0.0017°** (6″; the Moon, Anchorage 1955) |
| Ascendant, MC | ≤ 0.1° | **0.0006°** |
| Placidus cusps | ≤ 0.1° | ≤ 0.0006° |
| Retrograde flag | equal | equal wherever \|speed\| > 0.002°/day |
| ΔT | — | within 0.5 s of Swiss Ephemeris |
| Whole-sign cusps | equal | equal |

The charts cover 1900-01-01 to 2100-12-31. They include latitudes from -54.8° (Ushuaia) to 69.6°
(Tromsø, polar: Placidus falls back), six charts near 60° (Helsinki, St Petersburg, Anchorage,
Oslo, Reykjavik), and southern-hemisphere charts (Sydney, Hobart, Buenos Aires, Santiago, Cape Town,
Perth, Auckland, Lima, Nairobi). There are three unknown-time charts. DST cases cover gaps (London
1918, Auckland 1990, Chicago 2015), overlaps (Los Angeles 1980, London 2020), British Double Summer
Time 1941, British Standard Time 1969, US war time 1945, and half-hour and 45-minute zones.

## Birth time and time zones

* `BirthData.instant` = `ZonedDateTime.of(date, time ?: 12:00, zone)`. A time inside a **DST gap**
  moves forward by the gap; an **ambiguous** time uses the **earlier** offset. Swift must do the same
  (Foundation's `Calendar.date(from:)` resolves gaps forward; for the overlap, choose the earlier
  offset explicitly), and the golden test checks every chart's UTC instant.
* **Unknown time:** positions at local noon; no Ascendant, MC, houses or hour pillar.
  `moonSignUncertain` is set when the Moon changes sign during that local day, and
  `ChineseChart.boundaryUncertain` when a solar-term month boundary (including Lichun) falls on that
  day.
* **Historical tz caveat.** Since tzdata 2022 several zones are links to another zone unless the
  database is built with `backzone`, for example Atlantic/Reykjavik → Africa/Abidjan and
  Europe/Oslo → Europe/Berlin. Pre-1970 offsets for those places then differ between platforms:
  Java's tzdb omits backzone, while Linux system tzdata (and some Apple builds) include it. For
  Reykjavik in 1929, Java says UTC+0 while history (and Python on this PC) says UTC−1. The golden
  set therefore uses `Etc/GMT+1` for that chart. In the app, geocoding should store the
  `zoneId`, and the profile screen should show the resolved UTC offset for pre-1970 births so the
  user can correct it.

## Chinese zodiac and Four Pillars

| piece | rule |
|---|---|
| Year pillar | Sexagenary year starting at **Lichun**: the instant the apparent Sun reaches 315°, solved with Newton steps on our ephemeris (seconds-accurate). The birth instant is compared with it, so the result does not depend on time zone. Stem = (Y−4) mod 10, branch = (Y−4) mod 12 (1984 = 甲子). |
| Lunar-year animal | Shown alongside. The year begins on the bundled Chinese New Year date (1900-2100), compared with the local civil birth date. |
| Month pillar | Month k = ⌊((λ☉ − 315°) mod 360) / 30⌋ (the 12 "jie" terms: Lichun, Jingzhe, Qingming, …, Xiaohan). Branch = 寅 + k. Stem by the five-tigers rule: (yearStem mod 5)·2 + 2 + k. |
| Day pillar | Index = (JDN − 11) mod 60 = (epochDay + 17) mod 60, where 0 = 甲子. |
| Hour pillar | Branch = ⌊(hour + 1) / 2⌋ mod 12 (23-01 子, 01-03 丑, …). Stem by the five-rats rule: (dayStem mod 5)·2 + branch. |
| Clock (documented choice) | **Default: civil clock time as entered** (what birth records hold and what most popular apps use). `SolarTimeBasis.TRUE_SOLAR` is available: UTC + longitude/15 h + equation of time (Meeus 28.3). It moves the hour, and possibly the day, by up to ±2 h in wide zones such as China. |
| Zi hour (documented choice) | **Default `DAY_STARTS_AT_23`**: the day pillar advances at 23:00, the traditional rule. `DAY_STARTS_AT_MIDNIGHT` keeps the old day until 00:00 but gives 23:xx the next day's 子-hour stem (the "late Zi" school). |

How the Chinese data was verified (all in `ChineseZodiacTest`):

* **Solar terms:** all 4 800 solar terms from 1901 to 2100 match the Hong Kong Observatory tables
  to the civil date in UTC+8. Four terms from 1912-1928 fall within 12 minutes of midnight, where
  HKO's older tables differ from modern ephemerides (in both directions); the test allows only
  that window. Every Lichun date matches exactly.
* **Day pillars:** every day from 1900-01-01 to 2100-12-31 matches the independent arithmetic
  algorithm in Wikipedia's "Sexagenary cycle" article. Its worked examples anchor 1949-10-01 = 甲子
  and 1912-02-18 = 甲子. Also checked: 1900-01-31 = 甲辰 and 2000-01-01 = 戊午.
* **Chinese New Year dates:** taken from HKO for 1901-2100. 1900-01-31 is computed with Swiss
  Ephemeris; that same computation reproduces all 200 HKO dates except the three years where the
  naive "new moon before Yushui" rule fails (1985, 2034, 2053), for which HKO is used.
* **`testdata/golden_chinese.json`:** 56 cases from an independent Python oracle (Swiss Ephemeris
  + the Wikipedia day algorithm + HKO new-year dates). It covers births from Jan 20 to Feb 20
  around both Lichun and the lunar new year, ±3 minutes around Lichun in 7 years and zones, ±5
  minutes around month terms, every hour branch, late and early Zi, and unknown time.
* Bruce Lee's widely published chart (1940-11-27 07:12 San Francisco) gives 庚辰 丁亥 甲戌 戊辰.

## Blood type

`BloodType {A, B, AB, O}` plus an optional `RhFactor` that is display-only. Traits come from
`content_en.json`. The text always frames ketsueki-gata as folklore with no scientific basis.

## Palm features

`PalmAnalyzer.analyze` takes the 21 hand landmarks. They follow the MediaPipe Hand Landmarker
order, which matches Apple Vision's `VNHumanHandPoseObservation` joints one-to-one: 0 wrist, 1-4
thumb, 5-8 index, 9-12 middle, 13-16 ring, 17-20 little finger. It also takes the crease polylines
from the platform's edge analysis. Everything is converted to dimensionless measures, so photo
resolution does not matter:

* palm ratio = knuckle width (5→17) / palm length (0→9); square palm when ≥ 0.80;
* finger-to-palm = middle finger (9→12 along the joints) / palm length; long fingers when ≥ 0.88;
* hand shape: Earth (square palm, short fingers), Air (square, long), Fire (long palm, short),
  Water (long, long);
* line length = polyline length / palm width (heart, head) or / palm length (life, fate):
  short < 0.55 ≤ medium < 0.80 ≤ long;
* curvature = clamp((arc / chord − 1) × 5, 0, 1), curved when ≥ 0.35; depth comes from the
  detector's 0..1 contrast (deep ≥ 0.65, faint < 0.35);
* index : ring ratio (index finger longer when > 1.02, ring finger longer when < 0.98).

`PalmReadingPrompt.build` turns these into text. Its extra guardrail says lines are never
connected to lifespan, health, wealth or death. The image itself never reaches the core engines.

## Prompts and fallback text

* All prompts end with `HoroscopePrompt.GUARDRAILS`: entertainment only; no certainty or specific
  predictions; no danger, illness, death, pregnancy or breakup predictions; no medical,
  mental-health, financial, investment or legal advice; no "make a major life decision"; and the
  model must not mention the instructions. This extends Sundial's prompt.
* Prompts contain signs and whole degrees, never the birthplace, coordinates or names. Degrees are
  `floor`ed integers, so no locale- or rounding-sensitive formatting is involved.
* `ReadingCleaner.clean` strips label prefixes, markdown heading lines and emphasis, and
  surrounding quotes. It returns null for an empty answer, and the caller then shows the fallback.
* `FallbackReadings` builds readings from `content_en.json`. Choices are deterministic from the
  date and signs. The text reads as full paragraphs (see `testdata/golden_prompts.json`), so the app
  stays complete on phones without Gemini Nano or Apple Intelligence.
* `testdata/golden_prompts.json` pins the exact prompt and fallback strings for 3 charts, 2 pairs ×
  2 match kinds and 2 palms. iOS must reproduce them character for character.

## Regenerating data (scratch venv outside the repo)

```
python3 -m venv /tmp/cj-venv && /tmp/cj-venv/bin/pip install pyswisseph
# ephemeris files: https://github.com/aloistr/swisseph/tree/master/ephe (sepl_18.se1, semo_18.se1)
/tmp/cj-venv/bin/python testdata/tools/make_golden.py --ephe EPHE_DIR \
    --delta-t-out android/core/src/main/resources/com/metavirtuoso/conjunction/core/astro/delta_t.txt
/tmp/cj-venv/bin/python testdata/tools/make_golden_chinese.py --ephe EPHE_DIR
python3 testdata/tools/make_ephemeris_tables.py --vsop VSOP_DIR --meeus MEEUS_DIR \
    --out android/core/src/main/resources/com/metavirtuoso/conjunction/core/astro/ephemeris_tables.txt
python3 testdata/tools/make_chinese_calendar.py --hko HKO_DIR \
    --resource android/core/src/main/resources/com/metavirtuoso/conjunction/core/chinese/chinese_new_year.txt \
    --golden testdata/chinese_calendar.json
cd android && ./gradlew :core:writeGoldens && ./gradlew :core:test
```

Data sources: VSOP87D from IMCCE (`https://ftp.imcce.fr/pub/ephem/planets/vsop87/`). The Meeus
tables come as transcribed in `github.com/soniakeys/meeus` (MIT): `v3/moonposition/moonposition.go`
and `v3/pluto/pluto.go`. The Chinese calendar comes from the Hong Kong Observatory conversion tables
(`https://www.hko.gov.hk/en/gts/time/conversion1_text.htm`).
